# Automated data engine: audit and implementation plan

Status, 26 Nov 2026: phase 1 is running through GitHub Actions and its base migration is applied to Supabase. The 25 Nov daily run collected stream and chart snapshots; ranking history was partial because `ranking_snapshots` lacked the `job_id` field expected by the writer. The additive follow-up migration `database/automation_ranking_job_link.sql` repairs that schema gap. Daily snapshots are stored in Supabase; the visible ranking and its displayed dates publish weekly.

### Runbook

1. Apply `database/automation.sql` in the Supabase SQL editor. It is safe to run more than once. Apply each follow-up `database/automation_*.sql` migration once in order.
2. In GitHub, open Settings → Secrets and variables → Actions, and add `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`. Without them every run is a dry run.
3. Go to Actions → Data engine → Run workflow:
   1. Run `backfill` with dry run off, to import existing history.
   2. Run `daily` with dry run on, to see a live collection.
4. From then on, the schedule runs daily collection on Tuesday to Sunday at 05:00 UTC, and the edition every Monday at 06:00 UTC.

Re-running a period does nothing unless it failed or stalled for two hours. Failures show as a failed Actions run, which GitHub emails to the repo owner, with details in `ingestion_logs`.

Dry run on your own machine (stores nothing):

```
node ingest/run.cjs --job backfill --dry-run
node ingest/run.cjs --job daily --dry-run --providers turntable
```

Database test: `PGLITE_MODULE=<path to @electric-sql/pglite> node scripts/test-automation-db.cjs`.

### Not in phase 1

- **Daily stream numbers on the live site.** Scores are recalculated from the newest ledgers on every build, so the site updates on Mondays only. Showing daily counts without moving ranks needs a frozen score input per edition (phase 2).
- **YouTube, Deezer, Spotify API and Apple adapters, history graphs, admin dashboard, reports:** phases 2 to 4.

## 1. What exists today

### Architecture

| Layer | What it is |
| --- | --- |
| Frontend | Static HTML and vanilla JS, plus small React/Motion bundles built with esbuild. Pages are generated by `npm run build` (`scripts/build.cjs` → `scripts/render-*.cjs`) from JSON in `data/`. |
| Data store for charts | JSON files committed to Git: `data/current.json`, `all-time.json`, `nigeria-top100.json`, `releases-2026.json`, `streaming-catalogue.json` and others (36 files). |
| Serverless API | Vercel functions in `api/` (`data`, `rankings`, `view`, `edition`, `card`, `product`, …). They read the same bundled data. |
| Database | Supabase: profiles, receipts, votes, comments, watch list, touring editors and drafts, newsletter, Pro billing, signals. Charts are **not** stored in Supabase; `chart_editions` and `artist_metrics` exist but are secondary. |
| Scheduled jobs | Vercel crons: Sunday newsletter draft and watch digest. pg_cron: weekly bracket results. Edge function `edge/listeners.ts`: daily monthly-listener refresh with a per-day lease in `refresh_runs`. |
| Deploy | Push to GitHub `main` → Vercel builds and deploys. |

### Data pipeline

`npm run refresh:data` (`scripts/refresh-streaming.cjs`) runs, in order:

1. Archive the current edition into `data/current-editions.json`.
2. Python collectors in `scripts/research/`: TurnTable official charts, the 2026 release audit (Kworb song and album ledgers), Apple release-identity checks, release compilation, TurnTable categories and artist bios.
3. `finalize-refresh.cjs`: recalculates Current scores and movement.
4. Full site build.

It is run by hand and the result is committed. The last seven editions span 7 Sep to 15 Nov 2026.

The methodology in `docs/streaming-methodology.md` already follows the rules in the brief:
- Source dates are kept separate from check dates.
- Failed fetches keep the last good data.
- Stream counts are never inferred from charts or popularity.
- YouTube views stay separate from audio streams.
- A provider enters the score only once every Current artist has comparable coverage.

### Security baseline

- RLS is enabled on public tables. Writes use the service role from server code only.
- Moderation and editorial publishing happen in the Supabase dashboard.
- Touring uses a server-checked `touring_editors` role, which can serve as the model for an admin role.
- Secrets are read from environment variables (`SUPABASE_SERVICE_ROLE_KEY`, `CRON_SECRET`, …). None are in the repo.

## 2. What each provider can honestly supply

| Provider | Access | Gives | Does not give | Label in the index |
| --- | --- | --- | --- | --- |
| Kworb (already used) | Public pages | Spotify per-track and per-album play counts, daily deltas | Other platforms | Observed Spotify count (third-party ledger) |
| TurnTable (already used) | Public chart payload | Official Nigerian chart positions and weeks | Streams | Chart position |
| YouTube Data API v3 | API key, 10,000 units a day | `viewCount` and publish date per video | Audio streams | Verified video views (kept out of the audio total) |
| Deezer public API | No key | Track and album metadata, `rank`, `nb_fan` | Stream counts | Popularity indicator |
| Spotify Web API | Client credentials | Track, album and artist metadata, followers. Popularity may be restricted for apps created after Nov 2024; to be verified with real credentials. | Stream counts | Metadata and popularity indicator |
| Apple Music API | Paid developer token | Catalogue metadata, storefront charts | Stream counts | Chart position |
| Certifications (TurnTable) | Public pages | Award level and date | Streams | Certification |
| Net worth | None | n/a | n/a | Editorial estimate only |

Every observation stores the provider, URL, metric type (verified count, estimated count, chart position, popularity, airplay or calculated score), the publisher's source date, the collection time and a confidence label.

## 3. Proposed architecture

```
providers (Kworb, TurnTable, YouTube, Deezer, Spotify, Apple)
  → collector (Node, one adapter per provider)
  → validation and normalisation
  → Supabase append-only snapshots + job log
  → ranking engine (existing scoring code)
  → data/*.json → static build → Vercel
```

### Why keep the static site

Pages, URLs and SEO stay exactly as they are. Supabase becomes the history store and job ledger. The published site is still built from JSON produced from that history, so a failed run can never blank a page.

### Scheduler: GitHub Actions (recommended)

The existing collectors are Python and Node scripts that write files. GitHub Actions runs them unchanged, can commit the regenerated JSON, and Vercel then deploys.

Supabase Edge Functions would mean rewriting every collector in Deno within short execution limits. Vercel crons cannot rebuild a static site.

| Job | Schedule (UTC) | Does |
| --- | --- | --- |
| collect | every 6 hours | Run all provider adapters and write snapshots. No publish. |
| daily | 05:00 | Validate, compute daily growth, refresh stats pages, commit if tests pass. |
| weekly | Monday 06:00 | Publish the new Current 50 edition, movers and weekly report. |
| monthly | 1st, 06:30 | Monthly summaries. |
| yearly | 2 Jan | Archive year-end statistics. |

Each job takes a lease row keyed by job and period in `ingestion_jobs` (the same pattern as `refresh_runs`), so retries cannot duplicate snapshots. Snapshot tables have unique keys on provider, entity, metric and source date. The workflow commits only when `npm test` passes, and otherwise logs the failure and keeps the last good data.

### Ranking cadence

The methodology compares each edition with the last published edition. I recommend refreshing stream statistics daily but publishing rank changes weekly, so "movement" keeps its meaning. A daily-rank option can be added behind a setting.

## 4. Database migrations (additive only)

New migration file `database/automation.sql`:

- `data_sources`: provider, base URL, access type, enabled, notes.
- `ingestion_jobs`: job, period key, status, started_at, finished_at, counts, error summary. Unique on (job, period key).
- `ingestion_logs`: job id, provider, level, entity, message (no secrets), created_at.
- `artists`, `tracks`, `albums`: stable IDs (slug, Spotify ID, ISRC, UPC, YouTube video ID, Deezer ID), each unique where present.
- `track_stream_snapshots`, `album_stream_snapshots`: provider, metric type, value, source_date, observed_at, source_url, confidence. Unique on (provider, entity, metric, source_date). Append-only.
- `artist_statistics`: provider, metric, value, period, source_date, observed_at.
- `chart_positions`: chart, week_start, week_end, rank, last_rank, peak, weeks_on, entity. Unique on (chart, week_end, rank).
- `ranking_snapshots`: board, edition date, rank, score, breakdown JSON, method version.
- `certifications`, `regional_rankings`: extend, do not replace, the current certification data.

Public read access covers published snapshots only. Only the service role can write. Existing tables are not altered except where noted, and nothing is deleted.

A one-time backfill imports the history already in `data/` (editions, chart weeks, release ledgers) with the original source dates. No missing periods are filled in.

## 5. Delivery phases

1. **Foundation.**
   - Migrations and the provider adapter contract.
   - Kworb and TurnTable adapters wrapping the existing scripts.
   - Job lease and logging.
   - The GitHub Actions workflow, with a dry-run mode that writes nothing.
   - Tests for idempotency, validation and retry/backoff.
2. **More providers and history.**
   - YouTube (curated official video IDs) and Deezer adapters.
   - Daily, weekly and monthly growth from snapshots.
   - Movers of the Week from published editions.
   - History graphs on artist, song and album pages, shown only where real points exist.
3. **Admin.**
   - `/admin`, server-side authorised against a new `admins` table, modelled on `touring_editors`.
   - Job status, last and next runs, failures, retry, per-provider manual sync (via GitHub `workflow_dispatch` from the server) and a snapshot viewer.
   - Weekly report in the dashboard and by email through the existing Resend setup.
4. **Optional sources.**
   - Apple Music storefront charts (needs a developer token).
   - Automated certification checks.
